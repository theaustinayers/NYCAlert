# NYC Alert

A TypeScript Discord bot and public incident dashboard for NYC Alert at nycalert.ai. It provides per-channel FDNY/NYPD alerts across Manhattan, the Bronx, Queens, Brooklyn, and Staten Island, with Broadcastify transcription, local Whisper fallback, incident updates, and a live incident map.

> **Integration status:** The dashboard monitors every playlist configured in `BROADCASTIFY_FEED_MAP` through the Calls API and can monitor the NYPD authenticated static stream separately. It segments NYPD audio locally for transcription and deletes each segment after processing. The live-call archive is bounded to the latest 100 records; public transcripts and public FDNY audio remain separately configurable.

## Requirements

- Ubuntu 24.04 LTS (or another Node.js host)
- Node.js 20.11+ and npm
- A Discord application and bot token with the `bot` and `applications.commands` OAuth scopes
- Your approved Broadcastify Calls / Live Feed API documentation and credentials before enabling ingestion
- Broadcastify static-feed Basic-auth credentials if enabling the NYPD static stream
- A local `whisper.cpp` executable and model for transcription (installed by the Ubuntu installer)
- An OpenAI API key for AI triage/summaries (`OPENAI_API_KEY`); transcription itself is local and has no per-minute Whisper API fee

## Local setup

1. Install Ubuntu 24.04 and clone/copy this project to the host.
2. Run the supplied installer from the project root with `sudo bash deploy/install-ubuntu.sh`. It installs Node.js 22, PHP CLI, ffmpeg, loopback-only Postfix and OpenDKIM, compiles whisper.cpp for CPU, downloads the `base.en` model, installs npm dependencies, builds the bot, creates a locked-down systemd service, and creates `/etc/nyc-alert-bot.env` from the example if it does not exist. Publish `/etc/opendkim/keys/nycalert.ai/nyc-alert.txt` as a DNS TXT record. Configure SPF for the server's sending IP and publish a DMARC TXT record at `_dmarc.nycalert.ai` (start with `v=DMARC1; p=none;` while monitoring); direct mail delivery also requires outbound TCP port 25.
4. Restrict the secrets file (`chmod 600 /etc/nyc-alert-bot.env`). During development, set `DISCORD_GUILD_ID` for faster command registration; global slash-command registration may take time to propagate.
5. Invite the bot to your server with the `bot` and `applications.commands` scopes and permission to view/send messages and attach files in the alert channel.
6. In a server text channel, use `/alerts add` to select a borough and agency; its optional `audience` parameter is `public` (default), `buff`, or `news` (News Media). Public subscriptions route on public newsworthiness, Buff on buff-interest score, and News Media on assignment-desk score. `/alerts list` shows each audience, and `/alerts remove` accepts the audience to remove (legacy subscriptions without an audience are treated as News Media). Subscriptions are stored in `DATA_DIR/subscriptions.json`.
7. Set `BROADCASTIFY_CALLS_ENABLED=true` and configure every authorized playlist in `BROADCASTIFY_FEED_MAP`. `BROADCASTIFY_POLL_INTERVAL_MS` defaults to 60000; with five playlists this is about one API request per minute total and checks each playlist about every five minutes. Increase it to reduce requests, at the cost of slower discovery. When a Calls API record includes its documented `transcription` field, the bot uses that text directly and does not download audio or run Whisper; otherwise it falls back to the approved audio URL and local Whisper. To monitor the NYPD static feed, set `BROADCASTIFY_NYPD_STREAM_ENABLED=true`, `BROADCASTIFY_NYPD_FEED_ID`, `BROADCASTIFY_STATIC_USERNAME`, and `BROADCASTIFY_STATIC_PASSWORD` in the protected service environment. Do not put credentials in source control or logs.
8. The dashboard's **Live Radio Calls** tab lists processed transmissions and triage. Set `DASHBOARD_PUBLIC_TRANSCRIPTS=true` only after deciding that publicly displaying radio transcripts and AI summaries is appropriate. Set `DASHBOARD_PUBLIC_AUDIO=true` only when your terms permit publicly serving and retaining FDNY call audio. This opts in to an additional media download for FDNY Calls API records and enables playback in the public dashboard; it can increase Broadcastify usage/cost. For a published incident, the approved audio remains available across service/platform restarts until that incident is removed from the job board. Deleting the incident removes its audio reference and file. Leave this false to use Broadcastify transcripts without fetching audio. NYPD recordings are never retained or served by this application. Keep `BROADCASTIFY_AUDIO_REDISTRIBUTION_ALLOWED=false` if you do not want audio attached to Discord alerts.

### Dashboard accounts and administrator access

The dashboard header provides **Log in** and **Register** controls. Selecting **Buff** or **News Media** prompts users to sign in or register; access is granted only to an approved account of the matching type. The Ubuntu installer sets up PHP `mail()` with loopback-only Postfix and OpenDKIM, and generates `/etc/opendkim/keys/nycalert.ai/nyc-alert.txt`; publish that DKIM TXT record and configure aligned SPF and DMARC DNS records before relying on delivery. Direct delivery requires outbound TCP 25 and working mail DNS. Verification and staff invitation emails are sent as `NYC Alert <noreply@nycalert.ai>` using a responsive branded HTML template with a plain-text fallback. New accounts must verify their email and then wait for administrator approval; neither audience is automatically approved.

Accounts choose a unique 3–24 character username using letters, numbers, and underscores. This handle is the account's public-facing identity for future community features; first and last names are retained for account administration but are excluded from user-facing session/profile responses. Authorized administrators can see private account details in the admin console. Reviewers, moderators, and other invited staff choose their username during invitation activation. Existing accounts receive a stable generated `member_…` handle on load and can change it from **Profile**.

Set `ADMIN_EMAIL` and a unique `ADMIN_PASSWORD` of at least 16 characters to configure the bootstrap administrator. In the header's **Admin dashboard**, use **Administrators** to send additional admin invitations. Invited admins receive a one-time, 24-hour email link and must choose a unique password of at least 16 characters; the link token is stored hashed and kept in the URL fragment. Admins can revoke other admin accounts, but cannot revoke their own account or remove the last active administrator. The bootstrap admin is configured on the server and is not managed in the dashboard. The review panel also approves verified audience registrations, suspends, restores, or deletes accounts. Keep credentials out of source control. Login and invitation attempts are rate-limited by client source and account; auth mutations require same-origin requests. `TRUST_PROXY=true` is set by the supplied Nginx/HTTPS installer; for an existing proxy setup, enable it only if the app is reachable exclusively through that trusted proxy. Otherwise leave it false to prevent spoofed forwarded-IP headers. Sessions are HttpOnly, SameSite cookies and expire after 12 hours; sessions are cleared when the service restarts. For local HTTP development, set `DASHBOARD_PUBLIC_URL=http://localhost:8080` so the browser can use the non-Secure development cookie; use HTTPS in production.
Approved Buff and News Media users can manage up to **10 Discord or Slack incoming webhooks** from the dashboard account controls. Each destination can be limited to selected boroughs; it receives only new incident publications and matched incident updates that meet that account type's configured audience score and confidence rules. Routine calls and private pending reports are not delivered. Webhook requests contain the published incident summary and permalink, never source audio or raw radio transcripts. Only HTTPS endpoints on the exact Discord or Slack incoming-webhook hosts and path formats are accepted; redirects are not followed, requests time out, and deliveries are bounded in concurrency. Incoming webhook URLs contain bearer credentials: they are stored in the private `DATA_DIR/accounts.json` file, so restrict and back up that directory securely. The application does not return endpoint URLs in account or admin API responses; users should treat a URL as unrecoverable after submission and rotate it with Discord/Slack if exposed. Admins can suspend/resume individual destinations, suspend all webhook access for an account, or delete a destination in **Admin → Webhooks** / **Users**. Suspended accounts and destinations are excluded from delivery. Delivery is best-effort with no durable retry queue; check the service logs for aggregate delivery outcomes.

### AI Learning Debugger

Set `AI_LEARNING_LOG_ENABLED=true` in `/etc/nyc-alert-bot.env` and restart the service to enable transcript-only workflow logging. `AI_LEARNING_LOG_RETENTION_DAYS` defaults to 30; `AI_LEARNING_LOG_MAX_EVENTS` defaults to 20,000. Records are private JSONL at `${DATA_DIR}/learning-debug.jsonl` (mode `0600` in a mode `0700` data directory). They include the transcript once, source/group and time, AI headline/summary/category/confidence and audience scores, thresholds, extracted address/units/Box, geocoder result, correlation candidates, pending-queue decision, incident ID, and Discord routing outcome. No audio file, audio bytes, or audio path is copied into this log. Transcripts can still include sensitive radio information; use only an access-controlled server and set retention to fit your policy. In **Admin → AI Learning Debugger**, admins can inspect recent records, export the retained JSONL, or clear the log. Exported files require the same care as the original log. This produces an offline analysis dataset; it does not automatically train OpenAI or change the model.

The logged `confidence` is triage evidence-fit confidence: how well the transcript supports the proposed classification and extracted facts. It is not transcription/ASR quality and is not verification that the reported incident occurred. No ASR confidence is recorded unless a transcription provider supplies one. FDNY triage rows may additionally record versioned literal radio-code/phrase spans, explicitly spoken floor/building/occupancy mentions, and Queens-style hyphenation candidates derived from the triage location. These are review-only annotations: they do not select or geocode a candidate, alter scores, publish an incident, or assert code meaning. The NYC Open Data FDNY alarm-box point dataset is documented as last data-updated October 2019 and represents physical box locations, not incident locations, so it is not used to pin incidents. To analyze a private exported JSONL without printing transcript, address, or event-ID data, run `npm run audit:learning-log -- <path-to-learning-debug.jsonl>`. This reports aggregate stage counts, missing workflow stages, triage location/category/type coverage, observed thresholds, and Discord delivery outcomes only. Keep the source log local and protected; do not commit it or send it to public services.

#### Offline pipeline regression and evaluation

Use reviewed cases to improve the website's deterministic pipeline code before considering any model fine-tuning. Run `npm run evaluate:correlation` for the bundled Series 4/5-inspired correlation regressions. They use synthetic addresses and carry `synthetic-unverified` labels: they protect against code regressions but are **not** ground truth about the real incidents. The evaluator reports false merges separately from missed matches and never calls OpenAI.

For a genuinely labeled evaluation set, create a private JSONL file containing one case per line with `id`, `labelStatus` (`human-reviewed` or `adjudicated`), `expectedSameIncident`, and `existing` / `incoming` incident identities. Each identity permits only agency, borough, incident type, curated event description, location, coordinates, unit IDs, Box numbers, and event time. The loader rejects unknown fields (including transcripts), unreviewed labels, oversized values, and files larger than 5 MB. Use random case IDs; do not include raw production call IDs. Run `npm run evaluate:correlation -- <private-reviewed-cases.jsonl>`. The JSON report contains only aggregate metrics and case IDs for failures, not addresses or descriptions. Keep this dataset access-controlled and outside Git. Never turn the Series 4 export directly into labels: confirm suspicious transcripts, locations, and incident matches with a human first.

This is an **offline regression/evaluation pipeline**, not online learning. It can test correlation changes against reviewed labels; it does not train OpenAI, rewrite prompts, adjust thresholds, or deploy behavior automatically. Any future triage/transcription evaluation should use separate task-specific labels and explicit approval before sending any transcript to a hosted model.

Series 5-derived safeguards: addressless FDNY operational reports can match an explicit same-borough Box for the existing 30-minute incident horizon when there is one unique candidate and no conflicting concrete incident type or precise coordinates. Bare Box numbers do not establish identity across boroughs. A different reported address remains a veto unless the incoming transcript explicitly describes an address correction, shares a same-borough FDNY Box, has a compatible concrete type, and is within ten minutes; conflicting precise coordinates or explicit boroughs still veto that correction. Corrections retain the previous reported address in update history. Borough-only and unlocated updates do not replace a validated address/pin. A lower-score "No Fire Found" headline remains a timeline observation rather than erasing the established headline and summary; this is not claim-level verification of the radio report.

Known silence/noise-only transcript annotations (including repeated silence, crickets, static and unintelligible markers) are discarded before AI triage. Mixed speech and noise are preserved. This is a **post-transcription gate**, not a speech-probability/audio-quality detector before Whisper; pre-ASR quality classification, broad medical editorial restrictions, multi-format location resolution, durable incident lifetimes, and semantic/claim-level scope analysis remain separate work.

The installer is for Ubuntu 24.04 on a CPU host. It does not install a GPU/CUDA stack. It builds whisper.cpp and downloads the English `base.en` model; ffmpeg converts incoming MP3/MP4 audio to the 16 kHz mono WAV format used by the CLI. Tune `WHISPER_THREADS` to the server's capacity or use a larger model after measuring latency and memory. Local Whisper removes hosted transcription charges but uses your server's CPU/RAM/storage. AI triage/summaries still use the configured OpenAI API and may incur separate charges.

The Discord bot can start with feed integrations disabled. Broadcastify-provided FDNY call transcriptions are preferred to improve transcript fidelity and avoid audio retrieval/Whisper work where available; local Whisper is the fallback for records without text. AI triage still uses `OPENAI_API_KEY`. The NYPD authenticated stream is segmented by ffmpeg into 90-second mono PCM WAV windows by default; files are removed after processing. Fixed windows do not identify speakers or reliably line up with dispatch incidents, so transcripts can start/end mid-transmission. The model may extract only an address, cross street, or named place that is explicit in the transcript; it must not invent one. No system can guarantee that 95% of noisy radio calls contain a usable location.

Set `NEWSWORTHINESS_THRESHOLD` (Public, default `4`), `BUFF_INTEREST_THRESHOLD` (default `4`), and `NEWS_MEDIA_DESK_THRESHOLD` (default `4`) to integers from 1 to 5. The model assigns independent Public, Buff, and assignment-desk scores. Discord audience subscriptions route against their corresponding score, with non-routine and confidence checks. The website starts on Public and has Buff and News Media tabs, showing the selected score and all three scores. Ordinary dispatch and unconfirmed alarms are treated conservatively. Similar transcripts and alert summaries from the same agency/borough are deduplicated in memory for ten minutes. These are model judgments, not factual determinations; duplicate suppression resets when the process restarts.

### Optional X incident posts

Automatic X posting is disabled by default. To enable it, create an X developer app with user-context write access, then configure **either** an OAuth2 user token with the documented post-creation scopes in `X_USER_ACCESS_TOKEN`, **or** all four OAuth 1.0a user credentials in `X_OAUTH_CONSUMER_KEY`, `X_OAUTH_CONSUMER_SECRET`, `X_OAUTH_ACCESS_TOKEN`, and `X_OAUTH_ACCESS_TOKEN_SECRET`. Set `X_AUTO_POST_ENABLED=true` only after adding the credentials to the protected server environment. `X_POST_DELAY_SECONDS` defaults to 60 (allowed range 0–300); during that window, a correlated radio follow-up can add units, Box numbers, or an improved location before the post is composed. The delay and incident state are in memory, so a service restart during the window loses that scheduled post. Automatic X posts exclude medical-classified incidents as a privacy safeguard. Never commit credentials or paste them into chat; if exposed, revoke/rotate them. NYC Alert posts only newly published incidents that meet the Public newsworthiness threshold; it does not post routine traffic, buff/news-only alerts, unlocated pending reports, or follow-up updates as new posts. Posts include the AI call type, available radio-reported address, borough, units/Box where available, and hashtags. They deliberately omit URLs to avoid X's higher-priced Create Post with URL category; the canonical incident page remains available on NYC Alert but is not linked from the X post. `#Breaking` is included only for Public score 5/5. Posts that do not fit the X 280 weighted-character limit are skipped rather than silently truncating details. X API failures are logged separately and do not block Discord delivery; the app does not automatically retry an uncertain create-post request, to avoid duplicates. X API access, tier pricing, rate limits, and automation rules are controlled by X and must be reviewed before enabling. See the [X API Create Posts documentation](https://docs.x.com/x-api/posts/create-post).

## Public web dashboard

The dashboard starts with the bot at `http://<host>:8080` by default (`DASHBOARD_HOST` and `DASHBOARD_PORT` configure the listener). It shows FDNY borough playlists, FDNY Citywide call references, and the NYPD Citywide 1/2/3 feed page in a left-side source panel. Feed cards show online/offline/monitoring status, calls seen, and time since last audio activity; they do not link out to Broadcastify or play/relay source audio.

The incident panel displays items published after AI triage accepts them at the configured confidence threshold. Readers can give each incident one thumbs-up or thumbs-down per browser device. Votes are durably stored in `DATA_DIR/incident-votes.sqlite`; only a hash of the browser's random vote ID is retained. Accepted votes are also added to the transcript learning log when that optional logger is enabled. Feedback is for offline model evaluation and does not verify an incident or change live triage scores. **Live Radio Calls** shows processed segments, including routine classifications, when calls are available. Public transcript and summary display is disabled by default; when enabled, the bounded in-memory call list is exposed through `/api/live-calls`. The dashboard distinguishes recent NYPD stream bytes from processed/transcribed calls so an online stream is not incorrectly labeled as having no activity merely because transcription is pending or failed. **Pipeline diagnostics** shows stage, last poll/call, processed/retried/failed counts, and recent error. Public MP3 redistribution is disabled by default. Enable it only if your Broadcastify agreement explicitly permits public redistribution; NYPD audio is always deleted after transcription and is never exposed through the dashboard or Discord.

The header and dashboard now use the supplied NYC Alert logo, black background, and `nycalert.ai` branding.

The incident map has its own 30-minute refresh and shows only incidents from the previous 30 minutes with confidently matched coordinates; it does not delete or filter the searchable Latest Incidents list. Borough-only matches are never treated as incident coordinates. A location-precision label distinguishes rooftop, street address, intersection, road segment, borough, place, and unresolved; only validated address/intersection/road-segment results may be pinned, and road-segment pins are approximate. New and updated pins are diffed in place via server events without reloading the browser, and stale pins are removed while preserving the user's map viewport. Exact transcript locations are geocoded through OpenStreetMap Nominatim (rate-limited to one lookup per second and cached in memory); this sends the location text to that service. Set `MAP_GEOCODER_CONTACT` to an operations contact email as requested by Nominatim. The dark basemap uses Esri's World Dark Gray Base tiles with attribution, avoiding a Carto API key requirement. Pins use the triage event type: medical, vehicle, fire, police, or other. Locations that cannot be matched inside NYC bounds are not pinned.

Published incidents, their complete update history, and incident votes are stored durably in `${DATA_DIR}/nycalert.sqlite`, with indexed borough, call-type, time, and coordinate fields plus SQLite full-text search. This is the shared canonical dataset for dashboard templates. The versioned read-only `GET /api/v1/incidents` API supports `q`, repeated `borough`, `callType=fire|ems|pd`, `limit` (up to 100), and `offset`; it returns a page and total count. `GET /api/v1/incidents/:id` returns one incident and `GET /api/v1/map-incidents` returns currently mappable incidents. These APIs expose curated published incidents and updates only—not Live Radio calls, raw transcripts, or audio. Existing votes in `incident-votes.sqlite` are imported into the unified database on startup. Same-origin clients can use the API by default; for an independently hosted MDT frontend, set `DASHBOARD_READ_API_ORIGINS` to a comma-separated allowlist of exact HTTPS origins. CORS is read-only and does not allow credentials or wildcard origins. Live Radio and pending correlation remain ephemeral and reset on restart. Incident audio references are also process-local and are not restored from the database after restart.

Calls and incidents have a separate broad **Fire / EMS / PD** classification for dashboard organization, alongside the detailed incident type (fire, medical, vehicle, police, other). Medical maps to EMS; fire to Fire; police to PD. Vehicle calls use FDNY→Fire and NYPD→PD as the broad grouping. Unspecified/other classifications remain unclassified rather than being guessed. The dashboard filter applies to both Latest Incidents and Live Radio; staff can set the broad type when manually editing an incident.

Latest Incidents can be sorted by **Smart**, **Newest**, or **Priority**. The incident list/search still refreshes every 15 seconds; map refresh is separate. Newly detected alerts are temporarily pinned at the top, softly sparkle, and are announced in a queued top-bar ticker for 25 seconds each.

Source-call processing uses a private SQLite ledger in `DATA_DIR` keyed by agency and source call ID, so replayed calls remain suppressed across restarts; failed processing attempts release their claim for retry. This prevents same-source-call replay duplicates but is not a transaction spanning SQLite, dashboard memory, Discord, and X; a durable incident/outbox design is still needed for full crash-safe exactly-once delivery. Follow-up radio transmissions are matched for up to 30 minutes using agency, compatible incident type, location, units, and explicitly reported Box numbers. Qualified calls with no stated location or no confidently geocoded location are held privately in a bounded in-memory pending queue for up to 30 minutes; they are attached only when one uniquely corroborating located incident arrives, otherwise they expire without a public incident card or Discord alert. If a location explicitly names a borough that conflicts with its receiving radio feed, the geocoder must confirm that borough or the call remains pending. If one report has only a borough-level location, a near-simultaneous same-borough report may join it only when distinctive event terms corroborate the same event (for example, an EDP setting fires in a train car); ordinary shared words such as "fire" do not qualify. If both reports have precise coordinates more than 500 m apart, the match is rejected. A unique match updates the existing dashboard incident and edits its original Discord message without another role ping. Ambiguous matches stay separate. Incident correlation and pending state remain in memory and reset on service restart.

Latest Incidents cards include Facebook, X, and copy-link share actions using each incident's detail permalink.

The borough controls below the map are independent filters. All five start enabled (green); click a borough to disable it (red). The selected set filters incidents, radio calls, feed cards, and map pins together, and is preserved in the page URL. **All On** restores all boroughs.

Because this is an unauthenticated public read-only dashboard, deploy behind a TLS reverse proxy, configure firewall/rate limits, and avoid publishing summaries/audio that could expose personal or sensitive information. Transcript visibility is disabled unless `DASHBOARD_PUBLIC_TRANSCRIPTS=true`; incident and live-call metadata are held in memory and clear when the bot restarts.

**Real-time limitation:** Broadcastify Calls polling is rate-limited to one request per five seconds and distributes requests across every configured playlist; polling latency therefore grows with playlist count. The NYPD static stream is consumed server-side over HTTPS with Basic authentication and segmented locally; it is not a word-by-word transcript. Static credentials must remain protected in environment variables. The Calls API media URL/response contract still needs to match the approved documentation. Only allow documented media hosts in `BROADCASTIFY_AUDIO_ALLOWED_HOSTS`; downloads are size-limited, failed calls do not advance the cursor, and temporary audio is deleted after processing unless an explicitly approved FDNY retention option is enabled.

### Pterodactyl (Node.js egg)

This app can run on Pterodactyl if your host provides a Node.js 20+ egg/container, allows outbound HTTPS to Discord/Broadcastify/OpenAI, and gives you a port allocation. It does not require an interactive shell after installation:

1. Upload the project files (including `package.json` and `package-lock.json`) using the panel file manager or deploy from Git if your panel supports it. Do not upload `node_modules` or `dist`.
2. Ensure the egg's install script runs `npm install` so it installs both runtime dependencies and the TypeScript compiler needed at startup. If your host requires a custom install command, ask its administrator to set this up; file-manager-only access cannot install npm packages by itself.
3. Set the startup command to `npm start`. The start script builds TypeScript and launches the service, so no manual build terminal is needed.
4. Add the required Discord values and other settings as Pterodactyl environment variables if the egg exposes them, or upload a protected `.env` file through the panel. Fill in `DISCORD_TOKEN`, `DISCORD_APPLICATION_ID`, `OPENAI_API_KEY`, and the approved Broadcastify JWT fields. `whisper.cpp` must also be installed in the container with its model file; the Ubuntu host installer does not run inside a Pterodactyl container. Set `NEWSWORTHINESS_THRESHOLD` from 1 to 5 to control alert volume. Keep Broadcastify processing disabled until authorized audio retrieval is complete.
5. Allocate a port in the panel and leave `DASHBOARD_PORT` empty so the app reads `SERVER_PORT` (or `PORT`). Keep `DASHBOARD_HOST=0.0.0.0`. If your egg does not expose either port variable, set `DASHBOARD_PORT` to the allocated port explicitly.
6. Start the server in the panel. The dashboard uses that allocation and displays feed health, call counts, and recent audio activity without sending visitors to Broadcastify. For a friendly domain and HTTPS, configure the host's proxy/domain feature to route to the allocated port.

Pterodactyl can run the Node app and dashboard, but hosting a publicly accessible site still depends on your provider exposing the allocated port or providing a reverse proxy/domain. Do not make this unauthenticated dashboard public until you have reviewed what summaries can expose; public MP3 playback remains disabled unless expressly permitted.

## Ubuntu 24 service deployment

Build and run under a dedicated, unprivileged Linux account. Keep `.env` outside source control, use `chmod 600`, and configure a persistent writable `DATA_DIR`. A sample hardened unit is in `deploy/nyc-alert-bot.service`; adjust its deployment paths and Node binary to your installation, create the service account, and set `DATA_DIR=/var/lib/nyc-alert-bot` in its protected environment file. Restrict filesystem access and outbound networking to what the service requires. Do not run as root.

For an existing Ubuntu installation, upload/extract the new project version to a separate staging directory (do not extract it over `/opt/nyc-alert-bot`), then run `sudo bash deploy/update.sh` from the updated project root. The script stages dependencies/build first, snapshots application files for rollback, and refuses to run if `DATA_DIR` resolves inside the replaceable app directory. It does not overwrite `/etc/nyc-alert-bot.env` or `/var/lib/nyc-alert-bot`; account records, admin roles, subscriptions, webhook assignments, and site settings stay in `DATA_DIR`. The transcript-learning JSONL also remains there unless an administrator clears it. A successful update includes a local `/api/health` check; on failure the script restores the app snapshot and restarts the service. Back up `DATA_DIR` separately for disaster recovery.

### Enable HTTPS for nycalert.ai with Let's Encrypt

Point the `nycalert.ai` DNS A record to this server first. If an AAAA record exists, it must also point to this server. Allow inbound TCP ports 80 and 443 in the hosting-provider firewall. Upload/extract the current project, then from its root on Ubuntu run:

```bash
sudo bash deploy/setup-letsencrypt.sh your-operations-email@example.com
```

### One-click GitHub updates

The Ubuntu installer provisions a root-owned updater service and systemd path trigger; the bot account can only create a request marker and cannot invoke arbitrary root commands. For an existing server, run `sudo bash deploy/install-github-updater.sh` from the updated repository root; a fresh install configures the same updater with `sudo bash deploy/install-ubuntu.sh`. Copy the printed public key and add it in the private repository's **Settings → Deploy keys** with **Allow write access disabled**. Keep `/etc/nyc-alert-updater/deploy_key` private, then restart `nyc-alert-bot`. An authorized Admin can use **Settings → Website updates → Update to new version**. The updater fetches `main`, stages and builds, snapshots app files, swaps only after the build succeeds, health-checks, and restores the app snapshot if a deploy or health check fails. It never replaces the protected environment file or `DATA_DIR`; database/data migrations themselves are not reversed by app-file rollback. Back up `DATA_DIR` separately.
The setup installs Nginx and Certbot, moves the app listener to `127.0.0.1:8080`, proxies public traffic through Nginx, requests a certificate for `nycalert.ai`, and enables HTTP-to-HTTPS redirection. The existing `/etc/nyc-alert-bot.env` remains untouched; a systemd drop-in overrides only dashboard host and port. Certbot's systemd timer handles renewals. Check with `sudo certbot renew --dry-run` and `curl -I https://nycalert.ai`.

## Completing the Broadcastify/AI integration

The remaining approved API detail needed to validate end-to-end retrieval is a sanitized live endpoint response showing exactly how the audio URL or media reference is represented, plus the documented media host and any authentication requirements. Do not add undocumented media hosts or endpoints. Other follow-up work includes:

- Configure `BROADCASTIFY_FEED_MAP` with the supplied FDNY playlist UUIDs. The FDNY Citywide call pages and NYPD Citywide feed link are references for the dashboard, not API playlist UUIDs.
- Confirm and test the live call response audio field and media-host allowlist; bounded polling, deduplication, retries, and temporary-file cleanup are implemented.
- Connect the provider to the audio/transcription/triage pipeline and route matched alerts to subscribed channels.
- Confirm source terms allow retaining, attaching, and redistributing MP3 recordings to Discord. Attachments must also remain within current Discord upload limits.
- Add operational tests with sanitized API fixtures and protect transcripts/audio as sensitive operational data.

## Safety and privacy

AI summaries can be wrong: they must remain cautious, clearly identified as AI-assisted, and not treated as verified emergency information. Do not publish personal details or infer identities/locations from uncertain audio. Radio audio and transcripts may contain sensitive information; define short retention, access controls, and deletion before production. Respect Broadcastify terms, applicable law, and official/public-safety guidance. This bot is not an emergency dispatch or public warning service.
